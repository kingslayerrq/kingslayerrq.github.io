THE ENGINEERING QUESTION

How do the rules
compose?

A card can deal damage several times, apply a buff, draw another card, or ask the player to choose a discard. Each effect also interacts with turn order, energy, status effects, card piles, and the interface.

I split those responsibilities into authored definitions, mutable runtime instances, queued actions, and centralized resolution. Buffs participate through focused hook interfaces; views listen to state-change events.

01 / ACTIONS & RESOLUTION

Make execution order explicit.

CombatManager queues energy spending and card play. Card rules create actions such as damage, block, draw, and buff application. These resolution actions delegate gameplay mutation to CombatSystem.

  1. Play request

    Queue the energy cost and a PlayCardAction for the selected card and targets.

  2. Evaluate rules

    Build a CardContext, match its trigger, and check every condition on an effect.

  3. Enqueue effects

    Effect implementations turn their configuration into concrete combat actions.

  4. Resolve in order

    Yield to each action’s coroutine, then invoke that action’s completion callback.

A queue that can wait for input

The same interface supports a quick state change and a player decision. A discard-selection action opens a prompt, yields until confirmation or cancellation, then queues a discard for the chosen cards.

The queue waits for the action’s coroutine. A callback marks that action complete; actions it enqueues remain in FIFO order. UI tweens can run independently.

CombatActionQueue.cs · resolution loop excerpt

while (combatActionQueue.Count > 0)
{
    QueuedAction current = combatActionQueue.Dequeue();
    yield return current.Action.ExecuteAction();
    Debug.Log("Resolved" + current.Action.GetActionDetails());
    current.Callback?.Invoke();
}

02 / EVENTS & EXTENSION POINTS

Rules react. Views observe.

The project uses different mechanisms for gameplay modification and presentation. That distinction makes it easier to follow who can change an outcome and who displays the result.

GAMEPLAY HOOKS

Opt into a behavior

Buff instances implement interfaces such as IOnBeforeDealDamage, IOnBeforeTakeDamage, and IOnTurnEnd. BuffManager dispatches only to matching handlers, then removes expired buffs.

EVENT PAYLOADS

Carry the operation

DamageEvent carries source, target, card type, and a mutable amount. Before-damage hooks transform that amount; after-damage hooks receive the same operation context.

C# EVENTS

Update the presentation

OnHealthChanged, OnBlockChanged, OnBuffsChanged, and pile-count events notify views. Combat and run state events coordinate their broader lifecycles.

Buff behavior stays with the buff

Strength adds stacks to outgoing Attack damage. Vulnerable multiplies incoming Attack damage by 1.5 and rounds up. Temporary Strength inherits the damage behavior and clears its stacks at turn end.

Reapplying a stackable BuffData asset adds stacks to its runtime instance. The manager handles storage and dispatch rather than a switch statement for every buff.

Health logic does not animate a bar

BaseUnitInstance updates health and emits current/max values. UnitHealthbar subscribes, sets its initial display, and animates the fill with DOTween. It unsubscribes when rebound or destroyed.

BuffListView follows the same observer pattern for icons, while card piles publish count changes for their counters.

Source: CombatHooks.cs · BuffManager.cs · DamageEvent.cs · BaseUnitInstance.cs · UnitHealthbar.cs. These are typed hooks and C# events, not ScriptableObject event channels.

03 / A DAMAGE ACTION, END TO END

A hit is a pipeline.

DmgCardEffect resolves its configured amount and creates one DamageAction per hit. ResolveDamage creates a fresh DamageEvent for each living target, so one target’s modifiers do not carry into the next target’s payload.

BASE ATTACK6Configured amount
ATTACKER HOOK8+2 Strength
DEFENDER HOOK12Ceil(8 × 1.5)
BLOCK → HEALTH712 − 5 block

Illustrative calculation from the inspected rules: an Attack card, 2 Strength stacks, Vulnerable, 5 block, and a target with enough health. This is an explanation, not a captured gameplay result.

Keep the order visible in code

Attacker modifiers run before defender modifiers. TakeDamage consumes block, applies the remainder to health, and emits UI notifications. Post-damage hooks run afterward.

The action’s completion callback checks target health; defeated units can enqueue a DefeatUnitAction with disposal as its callback.

CombatSystem.cs · short excerpt from ResolveDamage

source.BuffManager.OnBeforeDealDamage(source, damageEvent, this);
t.BuffManager.OnBeforeTakeDamage(t, damageEvent, this);

t.TakeDamage(damageEvent.Amount, damageEvent.Source);

source.BuffManager.OnAfterDealDamage(source, damageEvent, this);
t.BuffManager.OnAfterTakeDamage(t, damageEvent, this);

A useful API distinction: DamageEvent.Amount is the modified incoming damage, not actual health lost after block. Enemy damage also reuses DamageAction, but currently passes CardType.None; Attack-only modifiers therefore do not apply on that path.

04 / SCRIPTABLEOBJECTS & AUTHORING TOOLS

Author definitions. Instantiate state.

ScriptableObject assets hold reusable definitions. Runtime objects hold the values that change for an individual card or unit during play.

Compose effects in the Inspector

CardEffectData uses SerializeReference for polymorphic effects, configurations, and conditions. A rule combines a trigger, conditions that must all pass, an effect implementation, and its typed configuration.

The custom CardEffectDataDrawer provides type selection, condition reordering, validation messages, and creation of a matching config through the effect’s RequiredConfigType.

Reuse behavior across different cards

DmgCardEffectConfig supplies hit count, optional secondary targeting, and DynamicValue. DynamicValue combines a base amount with a bonus from current block or the number of Strike cards possessed.

CardInstance selects base or upgraded definitions without rewriting the shared CardData asset. Effect/config objects are serialized classes inside the asset; they are not all separate ScriptableObjects.

Source: CardData.cs · CardInstance.cs · CardEffectData.cs · DynamicValue.cs · CardEffectDataDrawer.cs · BuffData.cs.

05 / SYSTEMS AROUND THE COMBAT LOOP

From one turn to a branching run.

Turns, intents, and card movement

CombatManager exposes explicit setup, player, enemy, victory, and defeat states. Turn setup chooses enemy intents, resets energy, runs turn-start hooks, and queues block reset and draws.

Enemy intent implementations reuse actions for damage, block, healing, buffs, and shuffling cards. Selection currently chooses randomly from available intents; the snapshot is used for targeting, not a sophisticated planning policy.

Card movement carries a cause. A discard caused by a card effect can trigger OnDiscard rules, while end-turn cleanup does not take that same branch. Exhaustion has its own effect and buff hooks.

Procedural maps as a search problem

MapGenerator constructs a graph, marks reachable nodes, assigns fixed floor types, then searches for remaining node assignments. It selects the unassigned node with the fewest valid candidates—the minimum-remaining-values heuristic—and backtracks when a choice cannot be completed.

Candidate types are tried in a weighted order. Per-node seeds separate assignment and content generation. NodeFactory combines the result with configuration assets to create runtime encounters.

RunManager also derives separate RNG streams for map, loot, events, combat, and shops. Some paths still use UnityEngine.Random, so this is not a claim of fully deterministic replay.

Source: CombatManager.cs · CombatSystem.cs · BaseEnemyUnitInstance.cs · MapGenerator.cs · SeedUtility.cs · RunManager.cs.

06 / PROGRESSION, PERSISTENCE & DELIVERY

Keep progress beyond a single run.

PROGRESSION MODEL

Stable identity and rules

Catalogs connect asset IDs to card, character, and relic records. Unlock conditions include wins, bosses, and elite completions; CompositeUnlockCondition combines child rules with All or Any semantics.

PERSISTENCE

Versioned saves

IProgressionStore separates storage from progression logic. The local JSON store supports version migration, validates temporary writes, keeps a backup, and attempts recovery from an invalid primary save.

DELIVERY

Editor checks and WebGL

EditMode tests cover progression reloads, save migration, card ID preservation, and build configuration. The repository’s workflow runs tests before a WebGL build and itch.io upload; Discord SDK code is excluded from WebGL.

Source: GlobalProgressionManager.cs · LocalJsonProgressionStore.cs · CompositeUnlockCondition.cs · Assets/Editor/Tests · repository build workflow. Existing Unity tests were inspected, not rerun for this portfolio edit.

ENGINEERING REFLECTION

Make the next extension easier to reason about.

Specify the timing contract

FIFO order is explicit, but an action can enqueue more work. Focused tests around multi-hit damage, defeat callbacks, and turn transitions would make that nested ordering contract clearer. A richer damage result could distinguish incoming damage, absorbed block, and health lost for future reactive effects.

Separate scope from completeness

The project demonstrates substantial combat, authoring, map-generation, and persistence systems. Several noncombat node paths remain placeholders, and it is a learning recreation rather than a claim of full feature parity with Slay the Spire.

The portfolio walkthrough reuses my supplied gameplay recording and documents the inspected source. It does not claim a new Unity runtime or WebGL validation run.
